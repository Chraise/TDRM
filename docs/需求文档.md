# 宿舍报修管理系统 - 需求规格说明书

## 1. 引言

### 1.1 编写目的

本文档旨在明确“宿舍报修管理系统”的功能需求与非功能需求，为后续的系统开发、测试及验收提供基准。本系统旨在解决传统宿舍后勤维护中存在的“进度不透明”、“成本难核算”、“调度低效”等核心痛点。

### 1.2 项目背景

随着校区规模扩大和住宿人员增加，传统线下填单或简单的网上报修模式已成为管理瓶颈。主要问题包括：

- **学生端**：提交后即进入“黑盒”状态，无法实时获知维修进度。
- **管理端**：宿管难以统筹派单，缺乏对维修人员工作量、耗材使用、校园故障分布及维修成本的量化统计。
- **维修端**：缺乏标准化的作业记录与库存联动机制。

### 1.3 项目目标

构建一套数字化宿舍报修系统，实现核心业务流（报修-派单-维修-耗材-评价）的全流程闭环管理，并为后勤部门提供基于数据的决策支持。

---

## 2. 用户角色描述

系统包含三种核心用户角色，各角色的主要职责如下：

| 角色 | 描述 | 主要职责 |
| --- | --- | --- |
| **学生 (Student)** | 宿舍居住者，报修发起人 | 提交报修单、查看进度、验收评价。 |
| **宿管/管理员 (Admin)** | 系统管理者与调度员 | 审核工单、指派维修人员、管理楼宇与用户、监控库存与报表。 |
| **维修人员 (Worker)** | 维修执行者 | 接收派单、执行维修、录入维修结果、登记耗材使用。 |

## 3. 功能需求详情

### 3.1 模块一：工单全生命周期管理

此模块是系统的核心，需支持从工单发起到归档的完整状态流转（Pending -> Assigned -> InProgress -> Completed），此外，还有Cancelled已取消的异常工单。

### 3.1.1 报修发起（学生端）

- **REQ-1-1**：系统应允许学生用户提交报修申请。
- **REQ-1-2**：报修单填写应包含：故障摘要、详细描述、故障图片（支持上传）。
- **REQ-1-3**：系统应根据学生账号自动关联其所属的宿舍楼与房间号（也可以修改为qi'ta公共位置），锁定故障位置。
- **REQ-1-4**：在管理员接单前（状态为 Pending），学生可以取消报修单。

### 3.1.2 智能调度与派单（管理员端）

- **REQ-2-1**：管理员可查看所有状态为“待处理（Pending）”的工单列表。
- **REQ-2-2**：**多对多指派支持**：系统需支持将一个工单指派给一名或多名维修人员协同处理。
- **REQ-2-3**：智能指派：系统自动地指派一个手头待处理工单最少的工人
- **REQ-2-4**：指派完成后，工单状态自动更新为“已派单（Assigned）”，并向相关维修人员发送通知。

### 3.1.3 维修执行与记录（维修人员端）

- **REQ-3-1**：维修人员接单后，需点击“开始维修”，将工单状态更新为“维修中（InProgress）”。
- **REQ-3-2**：**维修记录录入**：维修人员不直接修改工单主表，而是生成独立的“维修记录”，包含：维修开始时间、结束时间、人工成本、维修结果描述。
- **REQ-3-3**：**完工确认**：所有被指派的工人的维修及记录填写完成后，系统将工单状态更新为“已完成（Completed）”。

### 3.1.4 评价闭环（学生端）

- **REQ-4-1**：工单完成后，系统应自动通知学生进行验收。
- **REQ-4-2**：学生可对服务进行评分（如1-5星）和文字评价。
- **REQ-4-3**：评价数据需回写至工单主表，作为服务质量考核依据。

### 3.2 模块二：库存与物料管理

本模块聚焦于维修过程中的“出库/消耗”管理，不涉及复杂的进销存采购流程。

- **REQ-5-1**：**库存校验**：在维修人员录入耗材时，系统必须检查`配件库存`表，确认当前库存是否充足。
    - 若库存不足，系统应拦截操作并提示。
    - 若库存充足，允许操作继续。
- **REQ-5-2**：**物料消耗记录**：系统需记录每次维修所使用的配件ID及数量，并在`物料消耗明细`表中生成记录。
- **REQ-5-3**：**自动扣减**：生成消耗记录的同时，系统必须原子性地扣减`配件库存`表中的当前库存量，确保数据一致性。
- **REQ-5-4**：**库存预警**：当某配件的当前库存低于设定的“预警阈值”时，系统应向管理员发出补货提醒。

### 3.3 模块三：数据分析与报表

为管理员提供可视化的数据看板，辅助运维决策。

### 3.3.1 实时关键指标 (KPI)

- **REQ-6-1**：**待处理积压**：实时显示当前状态为 Pending 的工单总数。
- **REQ-6-2**：**库存预警数**：实时显示当前库存低于预警值的配件种类数量。
- **REQ-6-3**：**本月绩效**：统计本自然月内状态变为 Completed 的工单总数。
- **REQ-6-4**：**用户规模**：统计系统当前注册用户总数。

### 3.3.2 多维度图表分析

- **REQ-7-1**：**工单吞吐趋势**：支持按日期范围筛选，展示“每日新提交工单数”与“每日完成工单数”的双折线对比图（默认近7天）。
- **REQ-7-2**：**工单全生命周期分布**：展示当前所有工单在五种状态（待处理、已派单、处理中、已完成、已取消）下的分布比例（饼图/环形图）。
- **REQ-7-3**：**故障高发区域 Top 5**：聚合计算各宿舍楼的累计报修量，展示报修最多的前5栋楼宇名称及数量。
- **REQ-7-4**：**核心耗材消耗趋势**：
    1. 自动识别近6个月累计消耗量最大的前5种配件。
    2. 展示这5种配件在最近半年的月度消耗趋势曲线。

## 4. 非功能性需求

- **NFR-1 数据一致性**：系统底层需依赖关系型数据库（MySQL InnoDB）的事务特性（ACID），特别是在“库存扣减”与“工单状态流转”环节，必须确保数据严格一致。
- **NFR-2 实时性**：学生提交报修后，管理员端应能尽快看到更新；维修进度更新后，学生端应实时可见。
- **NFR-3 易用性**：移动端（学生侧）界面需简洁，支持多文件上传功能；管理端（Web侧）需提供清晰的仪表盘视图。
- **NFR-4 边界控制**：系统仅关注维修端的物料消耗，不包含供应商管理、采购入库审批等复杂进销存逻辑。
