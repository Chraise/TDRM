# 一、目标

## 1. 综述

本文档描述了宿舍报修全流程管理系统的设计。该设计旨在通过关系型数据库（MySQL）构建一套能够闭环管理“报修-派单-维修-耗材-评价”核心业务流的后端存储方案，重点解决传统报修中“进度不透明”与“成本难核算”等问题。

## 2. 核心目标

本设计试图达到以下关键目标：

- “报修-派单-维修-耗材-评价”的全流程实现
- 报修进度实时显示
- 管理人员统筹优化派单（实现“一单多人“共同完成的扩展）
- 维修耗材库存管理
- 报表分析（包括维修配件消耗频次分析、故障分布分析和工地完成情况分析等）

## 3. 非目标

以下内容不在本次设计的范围内，以控制系统复杂度并聚焦核心维修业务：

- 复杂的进销存管理：本系统仅关注维修端的“出库/消耗”。

# 二、背景

随着校区规模的扩大和住宿人员的增加，传统的宿舍后勤维护模式已逐渐成为管理瓶颈。当前，报修虽然可以通过网上填写保修单进行，但是存在以下的问题：学生无法实时获知维修进度，提交后即进入黑盒状态；宿管人员难以统筹派单；维修人员的工作量、耗材使用情况、校园故障分布以及维修成本缺乏量化统计。

因此，我们需要构建一套新的数字化宿舍报修管理系统。该系统旨在将报修业务线上化，实现从报修发起、任务调度、现场维修到评价反馈的全流程闭环，同时为后勤部门提供基于数据的决策支持。

# 三、总体设计

## 1. 设计概念

本系统采用以工单为核心的关系型数据模型。系统底层依赖 MySQL (InnoDB) 存储引擎，利用其 ACID 特性保障库存扣减与状态流转的数据一致性。

### 2.1 工单全生命周期管理模块

本模块构建了从故障上报到评价归档的完整业务闭环，采用严谨的状态机机制驱动流程流转，底层依托高度关联的关系型数据库结构支撑。

- **工单发起与初始关联（阶段一）：**业务始于学生用户层。系统通过用户表鉴权后，允许学生提交报修申请。在创建报修工单记录时，系统不仅自动记录“故障摘要”、“详细描述”及“图片地址”，还通过外键强关联用户表（提交人）与宿舍楼表，精准锁定故障发生的空间坐标。此时工单状态初始化为**Pending（待处理）**，支持用户在管理员接单前进行撤回或修改。
- **智能调度与多维分配（阶段二）：**管理员通过后台筛选“待处理”列表进行调度。针对复杂的维修任务，系统引入了工单分配中间表，实现了工单与维修人员（User表中的工人类别）之间**多对多**的映射关系。这意味着一个工单可指派给多名维修工协同处理。指派完成后，工单状态流转为**Assigned（已派单）**，并通过系统通知即时触达维修人员。
- **维修执行与物料消耗闭环（阶段三）：**维修人员接单后点击“开始维修”，状态变更为**InProgress（维修中）**。
    - **作业记录：**维修的具体执行情况并不直接修改工单主表，而是生成独立的维修记录表数据。该表记录了“维修开始/结束时间”、“人工成本”及“维修结果”，确保了主单据的整洁与历史可追溯性。
    - **库存联动：**当维修涉及零部件更换时，系统触发物料消耗流程。前端选择配件后，后台逻辑首先查询配件库存表校验“当前库存”是否充足。校验通过后，系统在物料消耗表中生成明细记录（关联维修记录ID与配件ID），并同步执行库存扣减操作，实现实物库存与系统数据的实时一致性。
- **流程终结与反馈评价（阶段四）：**维修作业完成后，工单状态流转为**Completed（已完成）**。系统自动触发消息通知学生用户。学生在移动端对服务进行验收，其提交的“用户评分”与“用户评价”将直接回写至报修工单主表。这一反馈数据不仅标志着单次服务的业务流终结，也为后续的服务质量考核提供了核心数据来源。

### 2.2 数据分析与报表模块

本模块基于聚合查询能力，为管理员提供实时数据看板，旨在通过可视化数据辅助运维决策与资源调配。

- **实时关键指标监控：**系统首页实时计算并展示运维核心数据的当前快照：
    - **待处理积压：** 实时统计状态为 Pending 的工单数量，提示由于积压的任务。
    - **库存预警：** 扫描所有配件，统计“当前库存”低于“预警阈值”的配件种类数量，触发补货提醒。
    - **本月绩效：** 基于当前时间动态计算本月（自然月）内完成的工单总数，量化当月运维产出。
    - **用户规模：** 统计系统注册用户总数，监控服务覆盖范围。
- **多维度可视化分析：**后端接口支持动态日期范围筛选，提供以下四个维度的数据洞察：
    - **工单吞吐趋势分析：**采用双折线图对比展示指定周期内（默认近7天）的“每日新提交工单数”与“每日完成工单数”。该图表直观反映了故障发生的频率波动以及运维团队的处理能力，帮助识别是否存在处理瓶颈。
    - **工单全生命周期分布：**对工单库进行全量扫描，按 待处理、已派单、处理中、已完成、已取消 五种状态进行分组聚合。通过分布图表帮助管理者宏观掌握当前的运维负载结构。
    - **故障空间分布 Top 5：**通过关联 宿舍楼 与 报修工单 表，聚合计算各楼宇的报修总量，并自动筛选出故障频次最高的 Top 5 楼宇。该数据为针对特定楼宇进行专项检修或设施老化评估提供依据。
    - **核心耗材消耗趋势：**基于 物料消耗明细 表，系统首先计算近 6 个月内累计消耗量最大的前 5 种配件。随后，针对这 5 种核心配件提取最近半年的月度消耗数据，生成多数据集趋势图。这有助于识别高耗材及其季节性消耗规律，优化备件采购计划。

# 四、详细设计

## 1.**系统整体架构与技术选型**

### **1.1 系统架构设计**

### **1.1.1 架构模式**

本项目采用 **MTV (Model-Template-View)** 架构模式，这是 Flask 框架的标准架构模式，与传统的 MVC 架构在概念上对应，但更符合 Flask 的设计理念。

**MTV 架构在本项目中的具体实现：**

1. **Model（模型层）**：位于 `app/models.py`，使用 SQLAlchemy ORM 定义数据库实体模型。模型层负责：
    - 定义数据表结构（如 `User`、`RepairOrder`、`DormBuilding`、`SparePart` 等）
    - 定义实体间的关系（一对多、多对多等）
    - 封装业务逻辑方法（如 `User.set_password()`、`User.check_password()`）
    - 提供数据验证和约束（如唯一性约束、检查约束）
2. **Template（模板层）**：位于 `app/templates/` 目录，使用 Jinja2 模板引擎渲染 HTML 页面。模板层负责：
    - 定义页面结构和布局（如 `base.html` 基础模板）
    - 实现页面复用（通过 `{% include %}` 和 `{% extends %}`）
    - 动态渲染数据（通过 `{{ variable }}` 和 `{% for %}` 等语法）
    - 分离不同角色的视图模板（`admin/`、`student/`、`worker/`、`auth/`）
3. **View（视图层）**：通过 Flask Blueprints 组织，位于 `app/admin/`、`app/auth/`、`app/student/`、`app/worker/` 等目录。视图层负责：
    - 处理 HTTP 请求和响应
    - 调用模型层进行数据查询和操作
    - 执行业务逻辑（如权限验证、状态流转）
    - 渲染模板并返回 HTML 响应

### **1.1.2 分层设计**

### **表现层**

表现层采用前后端混合渲染架构，主要技术栈包括：

- **HTML5 + CSS3**：使用语义化 HTML 标签构建页面结构
- **Bootstrap 4**：采用 SB Admin 2 主题框架，提供响应式布局和组件库
- **JavaScript/jQuery**：处理前端交互逻辑，如表单验证、AJAX 请求
- **Chart.js**：用于数据可视化，在管理员仪表板中展示统计图表
- **FontAwesome**：提供图标库支持
- **Jinja2 模板引擎**：服务端模板渲染，实现动态内容生成

前端资源统一管理在 `app/static/` 目录下，包括：

- `css/`：样式文件（自定义样式和第三方框架样式）
- `js/`：JavaScript 脚本文件
- `img/`：图片资源
- `uploads/`：用户上传的报修图片

### **业务逻辑层**

业务逻辑层通过 Flask Blueprints 实现模块化组织，每个 Blueprint 对应一个功能模块：

- **`app/auth/`**：身份认证模块
    - 用户登录/登出
    - 密码重置（通过邮件）
    - 密码修改
- **`app/admin/`**：管理员模块
    - 仪表板数据统计
    - 用户管理（增删改查）
    - 宿舍楼管理
    - 报修单管理（派单、查看详情）
    - 配件库存管理
- **`app/student/`**：学生端模块
    - 报修单提交（支持图片上传）
    - 我的工单查询（支持状态筛选）
    - 工单详情查看
    - 工单评价
- **`app/worker/`**：维修工模块
    - 待办任务列表
    - 开始维修/完工填报
    - 配件消耗记录
    - 维修历史查询

每个 Blueprint 通过 `@bp.route()` 装饰器定义路由，并通过自定义装饰器（如 `@admin_required`、`@stu_required`、`@worker_required`）实现权限控制。

### **数据持久层**

数据持久层采用 SQLAlchemy ORM 框架，实现对象关系映射：

- **ORM 模型定义**：在 `app/models.py` 中使用 SQLAlchemy 2.0 语法（`Mapped`、`mapped_column`）定义数据模型
- **数据库连接管理**：通过 `Flask-SQLAlchemy` 扩展管理数据库连接池和会话
- **数据库迁移**：使用 `Flask-Migrate` 进行数据库版本控制和迁移管理
- **数据库支持**：支持 SQLite（开发环境）和 MySQL（生产环境，通过 PyMySQL 驱动）
- **查询优化**：使用 `joinedload`、`selectinload` 等策略优化关联查询，避免 N+1 查询问题

数据库配置通过 `config.py` 统一管理，支持通过环境变量或 `.env` 文件配置数据库连接字符串。

### **核心目录说明**

- **`app/__init__.py`**：应用工厂函数 `create_app()`，采用 Application Factory Pattern，负责初始化 Flask 应用、注册扩展和 Blueprints
- **`app/models.py`**：数据库模型定义，包含 6 个核心实体模型（User、RepairOrder、DormBuilding、SparePart、MaintenanceRecord、PartUsageDetail）及其关系定义
- **`app/decorators.py`**：权限控制装饰器，实现基于角色的访问控制（RBAC）
- **`app/templates/`**：Jinja2 模板目录，按功能模块组织，使用模板继承和包含实现代码复用
- **`app/static/`**：静态资源目录，包含 CSS、JavaScript、图片和第三方库文件

### **1.4 核心设计规范**

### **1.4.1 应用工厂模式**

项目采用 **Application Factory Pattern** 创建 Flask 应用，实现在 `app/__init__.py` 中的 `create_app()` 函数。这种模式的优势包括：

- **测试友好**：可以为不同测试场景创建不同配置的应用实例
- **多实例支持**：可以同时运行多个应用实例（如开发服务器和生产服务器）
- **延迟初始化**：扩展（如数据库、登录管理器）在应用创建时初始化，而非全局初始化
- **配置灵活**：通过 `config_class` 参数支持不同环境配置

```python
def create_app(config_class=Config):
    app = Flask(__name__)
    app.config.from_object(config_class)

    # 初始化扩展
    db.init_app(app)
    migrate.init_app(app, db)
    login_manager.init_app(app)
    mail.init_app(app)
    moment.init_app(app)

    # 注册 Blueprints
    app.register_blueprint(auth_bp, url_prefix='/auth')
    app.register_blueprint(admin_bp, url_prefix='/admin')
    app.register_blueprint(student_bp, url_prefix='/student')
    app.register_blueprint(worker_bp, url_prefix='/worker')

    return app

```

### **1.4.2 权限控制机制**

项目实现了基于角色的访问控制（RBAC），通过装饰器模式实现权限验证：

1. **角色枚举定义**：在 `app/models.py` 中定义 `UserRole` 枚举（`STUDENT`、`WORKER`、`ADMIN`）
2. **装饰器实现**：在 `app/decorators.py` 中实现通用装饰器 `role_required()`，并导出三个具体装饰器：
    - `@admin_required`：仅管理员可访问
    - `@stu_required`：仅学生可访问
    - `@worker_required`：仅维修工可访问
3. **使用方式**：在路由函数上使用装饰器，未授权用户访问时自动重定向到登录页面并显示提示信息
    
    ```python
    @bp.route('/index')
    @admin_required
    def index():
        # 仅管理员可访问的路由逻辑
        pass
    
    ```
    
4. **Flask-Login 集成**：结合 `Flask-Login` 的 `@login_required` 装饰器，实现登录状态检查

### **1.4.3 时区处理策略**

项目采用统一的时区处理策略，确保时间数据的一致性和准确性：

1. **存储策略**：所有时间数据以 **UTC**格式存储到数据库，避免时区转换问题
2. **显示策略**：前端显示时统一转换为 **Asia/Shanghai（东八区）** 时区，使用 `zoneinfo.ZoneInfo("Asia/Shanghai")` 进行转换
3. **实现方式**：
    - 后端：在 `app/admin/index.py`、`app/worker/routes.py`、`app/student/routes.py` 中使用 `ZoneInfo("Asia/Shanghai")` 进行时区转换
    - 前端：在 `app/static/js/utils.js` 中提供 JavaScript 函数，自动将 UTC 时间转换为本地时区显示
4. **时间计算**：涉及日期范围查询时（如"今天"、"本周"、"本月"），先计算本地时区的起止时间，再转换为 UTC 进行数据库查询
    
    ```python
    SHANGHAI_TZ = ZoneInfo("Asia/Shanghai")
    
    def local_today_range():
        """计算本地时区今天的起止时间（UTC）"""
        now_local = datetime.now(LOCAL_TZ)
        start_local = now_local.replace(hour=0, minute=0, second=0, microsecond=0)
        end_local = start_local + timedelta(days=1)
        return start_local.astimezone(timezone.utc), end_local.astimezone(timezone.utc)
    
    ```
    

### **1.4.4 其他设计规范**

1. **表单验证**：使用 `Flask-WTF` 和 `WTForms` 进行服务端表单验证，防止 CSRF 攻击，确保数据安全
2. **文件上传**：报修图片上传功能实现文件类型验证、安全文件名处理、唯一文件名生成（UUID），并支持异常回滚时删除已上传文件
3. **密码安全**：使用 `werkzeug.security.generate_password_hash()` 和 `check_password_hash()` 进行密码哈希存储，不存储明文密码
4. **邮件异步发送**：密码重置邮件通过 `threading.Thread` 异步发送，避免阻塞请求处理
5. **数据库查询优化**：使用 SQLAlchemy 的 `joinedload`、`selectinload` 等加载策略，避免 N+1 查询问题，提高查询效率
6. **代码组织**：遵循单一职责原则，每个 Blueprint 负责一个功能模块，模型、视图、表单分离，提高代码可维护

## 3.系统功能设计

本章节详细描述各功能模块的设计与实现逻辑，按照 Flask Blueprint 的模块划分（Auth、Student、Worker、Admin）进行组织，并结合数据库实体模型和业务状态流转进行说明。

### **3.1 认证与授权模块**

认证与授权模块负责用户身份验证、会话管理和密码安全功能，是整个系统的安全入口。

### **3.1.1 用户登录/登出**

### **功能概述**

用户通过账号（学号/工号）和密码登录系统，系统根据用户角色（`UserRole` 枚举：`STUDENT`、`WORKER`、`ADMIN`）自动重定向到对应的功能模块首页。

### **技术实现**

**会话管理机制**：

- 使用 `Flask-Login` 扩展管理用户会话状态
- 通过 `LoginManager` 配置登录视图和提示信息
- 用户模型 `User` 继承 `UserMixin`，实现 `get_id()` 方法返回用户ID（字符串格式）
- 登录状态通过 `current_user.is_authenticated` 属性判断

**登录流程**：

1. 用户提交登录表单（`LoginForm`），包含账号、密码和"记住我"选项
2. 后端验证表单数据：
    - 账号格式校验：纯数字，长度 4-20 位
    - 密码必填校验
3. 数据库查询：根据账号查询 `User` 表，使用 `check_password()` 方法验证密码哈希
4. 登录成功处理：
    - 调用 `login_user(user, remember=form.remember_me.data)` 创建会话
    - 根据用户角色调用 `get_redirect_url_by_role()` 函数重定向：
        - `ADMIN` → `/admin/index`（管理员仪表板）
        - `STUDENT` → `/student/index`（学生首页）
        - `WORKER` → `/worker/index`（维修工工作台）
5. 登录失败：显示错误提示，保持在登录页面

**登出流程**：

- 调用 `logout_user()` 清除会话
- 重定向到登录页面

### **3.1.2 密码重置**

### **功能概述**

用户忘记密码时，可通过邮箱接收重置链接，使用 JWT Token 验证身份后重置密码。

### **技术实现**

**密码重置流程**：

1. **请求重置密码**（`/auth/reset_password_request`）：
    - 用户输入注册邮箱
    - 后端查询 `User` 表验证邮箱是否存在
    - 如果邮箱存在，调用 `User.get_reset_password_token()` 生成 JWT Token
    - Token 包含用户ID和过期时间（默认 600 秒）
    - 使用 `Flask-Mail` 异步发送重置邮件（通过 `threading.Thread` 实现，避免阻塞请求）
2. **邮件内容**：
    - HTML 模板：`templates/email/reset_password.html`
    - 文本模板：`templates/email/reset_password.txt`
    - 包含重置链接：`/auth/reset_password/<token>`
3. **重置密码**（`/auth/reset_password/<token>`）：
    - 调用 `User.verify_reset_password_token(token)` 验证 Token：
        - 使用 `PyJWT` 解码 Token
        - 验证签名和过期时间
        - 返回对应的 `User` 对象或 `None`
    - 如果 Token 无效或过期，显示错误提示
    - 如果 Token 有效，显示密码重置表单（`ResetPasswordForm`）
    - 用户提交新密码后：
        - 验证两次密码输入一致（使用 `EqualTo` 验证器）
        - 调用 `user.set_password(new_password)` 更新密码哈希
        - 提交数据库事务
        - 重定向到登录页面

**安全特性**：

- Token 设置过期时间，防止长期有效导致的安全风险
- 邮件异步发送，不阻塞用户请求

### **3.3.4 完工填报与耗材登记（核心功能）**

### **功能概述**

维修工完成维修后，填写维修记录，包括维修结果、工时和消耗的配件，系统自动扣减库存并计算成本。

### **输入数据**

- **开始时间**（`start_time`）：维修开始时间，本地时区（Asia/Shanghai）
- **结束时间**（`end_time`）：维修结束时间，本地时区
- **维修结果**（`result_desc`）：故障原因分析和维修结果描述，文本字段
- **配件消耗**（`part_ids[]`、`quantities[]`）：配件ID数组和对应数量数组（可选）

### **业务逻辑**

**权限与重复提交校验**：

1. 权限验证：确保当前维修工在工单的 `assigned_workers` 列表中
2. 重复提交检查：查询 `MaintenanceRecord` 表，检查是否已存在当前维修工对该工单的维修记录
3. 如果已提交，提示"您已提交过该工单的维修记录，无需重复提交"

**时间处理**：

- 前端提交的本地时间（无时区）通过 `naive_to_utc()` 函数转换为 UTC 时间
- 计算工时：`duration_hours = (end_time - start_time).total_seconds() / 3600`
- 计算人工成本：`labor_cost = duration_hours * HOURLY_RATE`（时薪 50 元/小时）

**事务处理流程**（核心逻辑）：

1. **开启数据库事务**（隐式，通过 SQLAlchemy 会话管理）
2. **创建维修记录**：
    
    ```python
    record = MaintenanceRecord(
        order_id=order.order_id,
        worker_id=current_user.user_id,
        start_time=start_utc,
        end_time=end_utc,
        result_desc=form.result_desc.data,
        labor_cost=labor_cost
    )
    db.session.add(record)
    db.session.flush()
    
    ```
    
3. **处理配件消耗**（如果存在）：
    - 遍历前端提交的配件ID和数量数组
    - 对每个配件执行以下步骤（在同一事务中）： a. **库存校验**：
        - 查询 `SparePart` 表获取配件信息
        - 检查 `part.current_stock >= qty`，如果不足则抛出 `ValueError` 异常 b. **扣减库存**：
        - `part.current_stock -= qty`
        - 直接更新对象属性，SQLAlchemy 会自动生成 UPDATE 语句 c. **创建消耗明细**：
        - 创建 `PartUsageDetail` 记录，关联 `record_id` 和 `part_id`
        - `db.session.add(detail)`
4. **工单完成判断**：
    - 统计该工单的所有维修记录数：`completed_count = count(MaintenanceRecord where order_id = order.order_id)`
    - 获取工单指派的维修工总数：`total_workers = len(order.assigned_workers)`
    - 如果 `completed_count >= total_workers`：
        - 更新工单状态为 `OrderStatus.COMPLETED`
        - 设置 `order.finish_time = datetime.now(timezone.utc)`
        - 提示"所有维修人员均已完工，工单归档"
    - 否则提示当前进度（如"当前进度 2/3，等待其他同事完工"）
5. **提交事务**：
    - `db.session.commit()`：如果所有操作成功，提交事务
    - 如果任何步骤失败（如库存不足、数据库错误），自动回滚（`db.session.rollback()`）

    - 用于饼图展示
3. **Top 5 楼宇**（`top_buildings`）：
    - 按宿舍楼分组统计工单数，降序排列，取前 5 名
    - 使用 `JOIN` 关联 `DormBuilding` 和 `RepairOrder` 表
    - 用于柱状图展示
4. **配件消耗趋势**（`parts_consumption`）：
    - 时间范围：最近 6 个月
    - 数据项：Top 5 配件（基于最近 6 个月总使用量）的月度消耗趋势
    - 查询逻辑： a. 先查询最近 6 个月总使用量最多的 5 个配件 b. 再查询这 5 个配件每个月的消耗量（按 `RepairOrder.finish_time` 的月份分组） c. 使用 `func.date_format(RepairOrder.finish_time, '%Y-%m')` 提取年月
    - 用于堆叠柱状图展示，每个配件使用不同颜色

**前端展示**：

- 使用 Chart.js 库渲染图表
- 支持日期范围筛选，通过 AJAX 请求更新图表数据

### **3.4.2 工单调度**

### **功能概述**

管理员查看待处理工单，并将工单指派给一名或多名维修工，系统自动更新工单状态。

### **业务逻辑**

**工单列表查询**（`/admin/orders`）：

1. **筛选功能**：
    - 默认显示"活跃工单"（状态为 `PENDING`、`ASSIGNED` 或 `IN_PROGRESS`）
    - 支持切换到"历史工单"（所有状态）
    - 支持关键词搜索：工单ID、标题、报修人姓名、宿舍楼名称
2. **智能排序**：
    - 活跃工单：先按状态权重升序，再按提交时间升序（FIFO，最早提交的优先处理）
    - 历史工单：先按状态权重升序，再按提交时间降序（最新显示）
3. **数据预加载**：
    - 使用 `joinedload()` 和 `selectinload()` 预加载：
        - `RepairOrder.submitter`（报修人）
        - `RepairOrder.building`（宿舍楼）
        - `RepairOrder.assigned_workers`（已指派的维修工列表）

**派单操作**（`/admin/orders/dispatch/<order_id>`）：

1. **权限与工单校验**：
    - 使用 `@admin_required` 装饰器确保仅管理员可访问
    - 验证工单是否存在
2. **维修工选择**：
    - 表单字段：`DispatchForm.worker_ids`（多选字段）
    - 选项来源：查询 `User` 表，筛选 `role == 'Worker'` 且 `status == 1`（在职）的维修工
    - 表单验证：至少选择一位维修工
3. **派单事务处理**：
    
    ```python
    # 查询选中的维修工
    workers = db.session.execute(
        select(User).where(User.user_id.in_(worker_ids))
    ).scalars().all()
    
    # 更新工单的 assigned_workers 关系
    order.assigned_workers = workers  # SQLAlchemy 自动处理中间表更新
    
    # 如果工单状态为 PENDING，自动更新为 ASSIGNED
    if order.status == OrderStatus.PENDING:
        order.status = OrderStatus.ASSIGNED
    
    db.session.commit()
    
    ```
    
4. **中间表更新机制**：
    - SQLAlchemy 通过 `order_assign` 中间表（多对多关系表）管理工单与维修工的关联
    - 当设置 `order.assigned_workers = workers` 时，SQLAlchemy 自动：
        - 删除旧的关联记录（如果存在）
        - 插入新的关联记录
    - 中间表结构：`(user_id, order_id)` 复合主键
5. **状态流转**：
    - `PENDING` → `ASSIGNED`（如果工单原状态为待处理）
    - 如果工单已经是 `ASSIGNED` 或 `IN_PROGRESS`，仅更新指派关系，不改变状态
6. **成功反馈**：
    - 显示成功提示，包含工单号和指派的维修工姓名
    - 重定向到工单列表

**推荐维修工功能**（`/admin/api/recommend-worker`）：

- 算法：统计每个维修工的活跃工单数（状态为 `ASSIGNED` 或 `IN_PROGRESS`）
- 推荐逻辑：选择活跃工单数最少的维修工（工作负载最轻）
- 查询实现：
    - 使用 `LEFT JOIN` 关联 `order_assign` 和 `RepairOrder` 表
    - 按 `user_id` 分组，统计工单数
    - 按工单数升序排列，取第一条记录
- 返回 JSON 格式数据，供前端 AJAX 调用

### **3.4.3 工单详情查看**

### **3.4.4 库存管理**

### **功能概述**

管理员管理配件库存，包括新增、编辑、删除配件，以及快速补货和低库存预警。

### **业务逻辑**

**库存列表**（`/admin/inventory`）：

1. **低库存预警优先显示**：
    - 查询所有配件
    - 排序规则：低库存配件（`current_stock < warning_line`）优先显示，然后按配件ID降序
    - 使用 SQLAlchemy 表达式：`order_by((SparePart.current_stock < SparePart.warning_line).desc(), SparePart.part_id.desc())`
2. **数据展示**：
    - 显示配件名称、规格、当前库存、单位、单价、预警阈值
    - 低库存配件使用醒目标识（前端样式）

**新增配件**（`/admin/inventory/add`）：

1. **表单字段**（`SparePartForm`）：
    - `part_name`：配件名称（必填，最大长度 100 字符）
    - `spec`：规格型号（可选，最大长度 50 字符）
    - `unit`：单位（可选，如"个"、"米"、"升"）
    - `price`：单价（必填，非负数，保留 2 位小数）
    - `warning_line`：库存预警阈值（必填，非负数，默认 10）
    - `current_stock`：初始库存（可选，非负数，默认 0）
2. **数据验证**：
    - 服务端验证：使用 WTForms 验证器
    - 数据库约束：`part_name` 和 `spec` 的组合唯一性（通过 `UniqueConstraint` 实现）
3. **创建逻辑**：
    - 创建 `SparePart` 实例
    - 添加到数据库会话并提交
    - 显示成功提示，重定向到库存列表

**编辑配件**（`/admin/inventory/edit/<part_id>`）：

1. **数据加载**：
    - 根据 `part_id` 查询配件
    - 使用 `form = SparePartForm(obj=part)` 将数据库对象绑定到表单
2. **更新逻辑**：
    - 更新配件所有字段（除主键外）
    - 提交数据库事务
    - 显示成功提示

**快速补货**（`/admin/inventory/stock_in/<part_id>`）：

1. **表单字段**（`StockInForm`）：
    - `add_quantity`：入库数量（必填，必须大于 0）
    - `new_price`：最新进货单价（可选，如果提供则更新配件单价）
2. **补货逻辑**：
    
    ```python
    part.current_stock += add_quantity
    if new_price is not None:
        part.price = new_price
    db.session.commit()
    
    ```
    
    - 直接增加库存数量
    - 如果提供了新价格，更新配件单价（反映最新进货成本）
    - 提交事务

**删除配件**（`/admin/inventory/delete/<part_id>`）：

1. **关联检查**：
    - 查询 `PartUsageDetail` 表，检查是否存在该配件的使用记录
    - 如果存在历史使用记录，禁止删除（保证数据完整性）
2. **删除逻辑**：
    - 如果无关联记录，执行 `db.session.delete(part)`
    - 提交事务
    - 显示成功提示

**低库存预警机制**：

- 在库存列表页面，系统自动检测 `current_stock < warning_line` 的配件
- 前端使用醒目的样式（如红色标识）提示管理员
- 仪表板统计低库存配件数量，供管理员快速了解补货需求

### **3.5 系统状态流转总览**

### **3.5.1 工单状态流转图**

```
PENDING (待处理)
    ↓ [管理员派单]
ASSIGNED (已派单)
    ↓ [维修工开始维修]
IN_PROGRESS (处理中)
    ↓ [所有维修工完工]
COMPLETED (已完成)
    ↓ [学生评价]
COMPLETED + rating (已完成并已评价)

PENDING (待处理)
    ↓ [学生取消]
CANCELLED (已取消)

```

### **3.5.2 状态流转触发条件**

| 状态流转 | 触发操作 | 执行角色 | 关键逻辑 |
| --- | --- | --- | --- |
| `PENDING` → `ASSIGNED` | 管理员派单 | 管理员 | 更新 `order_assign` 中间表，设置 `assigned_workers` |
| `ASSIGNED` → `IN_PROGRESS` | 维修工开始维修 | 维修工 | 更新工单状态 |
| `IN_PROGRESS` → `COMPLETED` | 所有维修工完工 | 系统自动 | 统计 `MaintenanceRecord`，当完成数 >= 指派数时自动更新 |
| `PENDING` → `CANCELLED` | 学生取消工单 | 学生 | 仅允许取消待处理状态的工单 |
